## Hygiene gaps

### 5. A real dashboard data bug, found directly: task 225's `dept` value doesn't match any department id, and the two dashboard files handle the resulting undefined lookup differently — one degrades, the other would throw.

`internal/dashboard/design/Main.dc.html` line 887: `{ id: 225, title: 'Payment rail researched and decided...', dept: 'accounting', ... }`. The department registry (same file, lines 542–561) defines ids `web`, `arch`, `sales`, `ads`, `comms`, `acct`, `ctrl`, `content` — there is no `'accounting'`. The task-rendering code (line 917) does `const d = deptById[t.dept]; return { ...t, hue: d.hue, ... }` with **no fallback** — `deptById['accounting']` is `undefined`, so `d.hue` would throw a `TypeError` if this file's own JS is executed over this data. The published `sirketim-dashboard.html` carries the identical typo (line 1100) but its equivalent lookup (line 1167) has a defensive fallback: `DEPT_BY_ID[t.dept] || { hue: 240, short: t.dept || 'Unassigned', ... }`. So it doesn't crash there, but the effect is still wrong: task 225 doesn't match `t.dept === d.id` anywhere the department filter/chip logic runs (lines 1179, 1460), so it's invisible under the Accounting department view and undercounts Accounting's task tally by one real, substantial, `fulfilled` deliverable (the Paddle-to-Payoneer payment-rail decision). One-character-class fix (`'accounting'` → `'acct'`), concrete and verifiable.
