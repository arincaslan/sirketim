# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sirketim is a solo-founder, multi-department agency workspace, not a single codebase. Claude Code subagents act as each department's actual workers (drafting, research, first-pass production), not just copilots; the founder reviews and decides. Seven departments: web development, architecture (real building/interior design), sales, advertising, communication, accounting, control/audit. A three-member board (COO, CFO, Controller) sits between the founder and the departments — see `shared/board.md`.

## Commands

There is no build/lint/test at the repo root — every Next.js project (client or product) is self-contained, each with its own `package.json` scoped to its own subfolder. `cd` into the specific project before running anything; nothing installs or builds from the repo root.

Real projects exist today under `products/web-templates/`: `agency-landing/`, and three deliberately distinct fragrance e-commerce templates — `fragrance-store/` (warm cream/gold, rounded), `fragrance-store-2/` ("Nocturne" — dark obsidian/ember-red, sharp corners), `fragrance-store-3/` ("LUMEN" — cool mineral-stone/warm ivory, electric-lavender accent). Each new template's design direction is checked against the others' actual palette/typography before committing, specifically to avoid a third re-skin. Inside any of them: `npm install`, then `npm run dev` / `npm run build` / `npm run lint`. No test script is configured in any project yet — don't invent one. The same self-contained pattern applies once the `new-web-client` skill scaffolds a client under `departments/web-development/clients/<slug>/`.

Setting the workspace up on a different machine (tool installs, `gh`/Claude Code auth, MCP approval): see `SETUP.md`.

Commands that are already real and used in this repo:
- **Architecture CAD generation**: Python with `ezdxf` (DXF) and `svgwrite` (SVG) — already installed system-wide, driven through the department's own `departments/architecture/lib/cadgen/` library (data model + generator + compliance checker), not freehanded per project. See `departments/architecture/CLAUDE.md`.
- **Architecture DWG conversion**: ODA File Converter, run headless — `"<install path>\ODAFileConverter.exe" <inputFolder> <outputFolder> <outVer> <outType> <recurse:0/1> <audit:0/1>`. Installed per-user (machine-wide MSI install needs admin rights this environment doesn't have); `ezdxf`'s `odafc` addon needs its `win_exec_path` pointed at the real per-user install path or it silently looks in `Program Files` instead — see `departments/architecture/CLAUDE.md` and `departments/architecture/reports/cad-tooling-gap-analysis.md` for the exact path and gotcha.
- **Scanned-PDF reading**: Poppler (`pdftoppm`/`pdftotext`/etc., via winget) — required for the Read tool to render scanned/image-only PDF pages; without it, scanned intake documents (common in architecture zoning intake) fail to read. Installed system-wide.
- **Architecture 3D rendering**: Blender 4.5 LTS, run headless — `"C:\Program Files\Blender Foundation\Blender 4.5\blender.exe" --background --python <script>.py`. Installed via winget (`BlenderFoundation.Blender.LTS.4.5`), added to the user PATH. Note: `bpy` must be imported explicitly in the script; it isn't auto-imported.
- **MCP connector status**: `claude mcp list` shows configured servers; `/mcp` inside an interactive session approves a pending one. `.mcp.json` configures four: `openart` (OAuth, no API key), `21st` (21st.dev's Magic MCP — component search/generation for web-development, granted to `web-developer` as `mcp__21st`; needs `TWENTY_FIRST_API_KEY` set as a real local environment variable, referenced from `.mcp.json` as `${TWENTY_FIRST_API_KEY}` rather than committed — see `departments/web-development/CLAUDE.md`), `chrome-devtools` (Google's Chrome DevTools MCP, free, no API key, runs via `npx chrome-devtools-mcp@latest --isolated` — drives a real local Chrome instance for screenshots/console/network/perf, granted to `web-developer` as `mcp__chrome-devtools`), and `fanvue` (`https://mcp.fanvue.com/mcp`, added 2026-08-22, granted only to `ad-strategist`) — Fanvue's own official account/posting server (publish/schedule posts, analytics, vault, fan chat), unusable until a real KYC-verified Fanvue account exists, and gated separately from generation: publishing/reading data rides the founder's standing per-persona/platform authorization, but replying to fans or sending mass messages needs its own explicit founder go-ahead (same posture as Communication's manual-send policy) — see `departments/advertising/CLAUDE.md` "Fanvue account/posting". **Two AI-influencer content generators, `eromify` and `zencreator`, were configured 2026-08-22 and then REMOVED the same day** at the founder's direct, repeated instruction, after neither proved usable for free and a request to source a free "unrestricted" replacement was declined (see `departments/advertising/CLAUDE.md` "AI-influencer content" and memory `feedback_no_unrestricted_content_tooling` for the full reasoning — that reasoning holds regardless of price or where a tool is sourced from). No Fanvue-capable (+18) content generator is configured as of 2026-08-22; OpenArt was checked directly and confirmed incapable. Approval appears to be scoped per session/process, not global — a session can show `⏸ Pending approval` even after the founder approved it elsewhere, and a long-running session started *before* an env var was set (or before a server was added to `.mcp.json`) won't see it until a fresh session starts. **`claude mcp list` itself is not fully reliable** — confirmed 2026-08-21: it reported `openart` as pending in a stale session while a direct `mcp__openart__openart_account_get` call succeeded immediately (real account/credits returned). So don't stop at `claude mcp list`: if a connector matters for the task at hand, try calling one of its actual tools (or `ToolSearch` for `mcp__<server>__*`) — if the tool genuinely isn't in your available set, that's the reliable signal of real unavailability, not what the list command printed. This applies doubly to background subagents: they don't automatically inherit a fresh top-level session's connections, so verify independently inside the subagent rather than assuming a working connector up top means it works everywhere.
- **Third-party skill installs and the `.agents/skills/` directory**: `.claude/skills/` mostly holds skills authored for this repo (`new-web-client`, `project-brief`, etc.), but three external skill packages are now installed for the web-development department: `ui-ux-pro-max` (design-intelligence data, installed via `uipro init --ai claude`, npm package `ui-ux-pro-max-cli`) sits directly under `.claude/skills/ui-ux-pro-max/`; Emil Kowalski's animation/design skill set and `design-taste-frontend` (the "taste" skill, `Leonxlnx/taste-skill`) are both installed via `npx skills@latest add <repo>` (the latter with `--skill design-taste-frontend` to avoid its repo's 12 other bundled style/output variants) and land in a top-level `.agents/skills/` directory with `.claude/skills/<name>` symlinks pointing into it — that split is the installer's own convention (`.agents/skills/` is a cross-tool location it also symlinks into other agent CLIs' skill dirs), not something to fight. The `npx skills@latest add` installs (but not `ui-ux-pro-max`) are tracked in root-level `skills-lock.json` (source repo, path, content hash per skill) — check it before assuming a given skill's provenance or re-running an install. **Known gotcha**: `ui-ux-pro-max`'s installer bundles several other skills (`design`, `brand`, `banner-design`, `design-system`, `slides`, `ui-styling`) alongside it; its `design` skill has the same name as Anthropic's own built-in `design` skill (the Claude Design canvas one `internal/dashboard/` depends on) and shadows it if left installed. These six were deliberately removed after install — if `uipro init`/`uipro update` is ever re-run, delete them again rather than letting the shadow reappear.
- **Git remote**: this repo pushes to `https://github.com/arincaslan/sirketim` (GitHub CLI `gh` is installed and authenticated as `arincaslan`). The repo is **public**, not private — a deliberate tradeoff made to unblock claude.ai's GitHub connector (it only had public-repo scope), so treat the ledger and every department's strategy docs as publicly visible. Two claude.ai scheduled routines (`Sirketim Weekly Accounting Report`, `Sirketim Weekly Control/Audit Report`) run weekly against `main` via `board-cfo`/`board-controller`, writing into `departments/accounting/reports/` and `departments/control/reports/` and pushing directly — a `git pull` may surface new files you didn't create locally.
- **Cross-session sync (do this first, every session)**: the founder works from multiple Claude Code surfaces (this CLI, claude.ai web/mobile). Board subagents (`board-coo`, `board-cfo`, `board-controller`) have no Bash/git tool access — they only ever see whatever is already sitting in the local working tree's files when they're invoked. They cannot discover work that landed on a remote branch. So at the start of a session, and before answering any "what's going on" / status question or delegating to the board, run `git fetch origin` and check `git branch -r` plus `git log main..origin/<branch>` for real work sitting on unmerged branches (commonly named `claude/*` from other sessions). Surface or merge what you find before trusting the board's picture of current state — otherwise their report will be stale by exactly however much cross-session work hasn't synced to `main` yet.
- **Two physical machines, two different Windows usernames — a real, recurring path gotcha**: the founder works from two computers, one logged in as Windows user `win10`, the other as `Semih`. This repo is machine-portable (it's just git), but any **absolute local path this repo's code or docs hardcode** (`C:\Users\<name>\...`) is NOT portable across the two — it's silently wrong on whichever machine didn't write it. This already happened for real: `departments/architecture/lib/cadgen/export_dwg.py`'s `ODA_EXEC_PATH` was written against a `C:\Users\Semih\...` install and broke on the `win10` machine until caught and fixed (see `departments/architecture/CLAUDE.md`'s DWG-conversion gotcha and `departments/architecture/reports/cad-tooling-gap-analysis.md`). After any `git clone`/`git pull` on either machine, and before trusting a hardcoded local install path anywhere in this repo (Python scripts, department CLAUDE.md snippets, anything under `C:\Users\...`), check whether it matches `$env:USERNAME`/`whoami` on the machine you're actually on — if it names the other user, re-verify the real local install path on this machine and update the code/doc, don't assume it still resolves. This applies to any future per-user tool install (not just ODA File Converter) — machine-wide/system installs avoid the problem entirely when available; per-user installs need this check.

## Architecture

CLAUDE.md files nest and each layer adds scope, not a replacement: this root file -> `departments/<dept>/CLAUDE.md` -> `departments/<dept>/clients/<slug>/CLAUDE.md` (created per-client by a skill). Read the relevant chain before doing department or client work, don't rely on the root file alone.

- **Subagents** (`.claude/agents/`) map 1:1 to departments — `web-developer`, `architecture-assistant`, `sales-strategist`, `ad-strategist`, `communication-strategist`, `accountant`, `auditor`. Each is scoped to its department's CLAUDE.md, has only the tools that department needs, and should be invoked for department-specific work instead of doing it ad hoc from root.
- **Board members** (`.claude/agents/board-*.md`) are a layer above departments, not an 8th/9th department — `board-coo` (owns web development, architecture, sales, advertising, communication), `board-cfo` (owns accounting), `board-controller` (owns control/audit). The founder briefs a board member with an outcome; it delegates to the department subagent(s) it owns via the Agent tool and reports back a synthesized result. See `shared/board.md`. Prefer addressing the board member over the department subagent directly when the request is an outcome rather than a specific department task.
- **Skills** (`.claude/skills/`) are the repeatable intake-to-deliverable workflows: `new-web-client`, `project-brief` (architecture), `client-proposal` (sales), `campaign-brief` (advertising), `product-listing` (sales/products). Prefer these over freeform work when a task matches one.
- **`products/`** vs **`departments/<dept>/clients/`**: products are Sirketim's own sellable goods (web templates, architecture plan packs, POD prints), built by whichever department creates the underlying asset but sold by sales via marketplaces — separate from client-commissioned work. See `products/README.md` for the line breakdown.
- **`internal/dashboard/`** — the founder's single-page task board + charts (real assigned/fulfilled tasks per department, financial chart from the ledger, department report links). It's a **Claude Design canvas** (`internal/dashboard/design/Main.dc.html` + `canvas.json`), not a deployed Next.js app — there is no server, build, or `package.json` here. Edit `Main.dc.html` directly, then re-seed (`seed-canvas.mjs --out internal/dashboard/design/sirketim-dashboard.html`, the checked-in seeded file) and republish via the `design` skill's flow to the existing Artifact URL (ask the founder for it, or check memory/recent conversation — don't create a new artifact). Every task assigned or completed in a session should be reflected here before the turn ends, per the founder's standing instruction.
- **`shared/clients.md`** is the single cross-department client/lead registry (a client can span multiple departments). **`shared/board.md`** is the board charter (who's on it, what they own). **`shared/brand.md`** is Sirketim's own brand/voice, still a placeholder.
- **Connector status** lives in two places: `.mcp.json` (MCP servers, e.g. `openart`) and each department's CLAUDE.md "Recommended connectors" section (everything else, mostly not yet configured — check before assuming a connector is live).

## Departments

- [Web Development](departments/web-development/CLAUDE.md) — Next.js + Tailwind + shadcn/ui, GitHub, Vercel.
- [Architecture](departments/architecture/CLAUDE.md) — briefs, zoning research, to-scale CAD floor plans (DXF/SVG/DWG) via a shared `lib/cadgen/` Python library, 3D catalog renders (Blender + AI polish). Never claims permit-ready/stamped output.
- [Sales](departments/sales/CLAUDE.md) — client pipeline/proposals, plus productizing department output for near-zero-cost marketplace sales (Etsy primary).
- [Advertising](departments/advertising/CLAUDE.md) — OpenArt-generated content, organic-first posting (Instagram/TikTok, always SFW) plus a founder-gated Fanvue (+18) channel for AI-persona social accounts — currently no generator configured for it (`eromify`/`zencreator` removed 2026-08-22), paid spend only when budgeted or revenue-funded.
- [Communication](departments/communication/CLAUDE.md) — direct DM/email/phone outreach for Sirketim's own products; hands off interested prospects to Sales to close. No sending connectors configured yet (drafts ready for manual send).
- [Accounting](departments/accounting/CLAUDE.md) — manual ledger of income/expenses/subscriptions (no bank/Stripe integration yet), weekly financial report.
- [Control/Audit](departments/control/CLAUDE.md) — internal audit of the other departments: workflow correctness, registry hygiene, cross-department coordination, productivity/yield. Read-only over other departments' files; reports findings, doesn't fix them.

## Conventions

- Client work: `departments/<department>/clients/<slug>/`. Products: `products/<line>/<slug>/`. Slugs are lowercase-hyphenated.
- Register every client/lead in `shared/clients.md` as soon as they're qualified.
- Every transaction (income, expense, subscription charge) gets a row in `departments/accounting/ledger.md` when it happens, not retroactively at report time.
- Don't claim a connector, deploy, or post happened if it isn't actually configured — say what's missing instead.
