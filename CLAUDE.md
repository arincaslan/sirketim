# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sirketim is a solo-founder, multi-department agency workspace, not a single codebase. Claude Code subagents act as each department's actual workers (drafting, research, first-pass production), not just copilots; the founder reviews and decides. Eight departments: web development, architecture (real building/interior design), sales, advertising, communication, content (long-form/affiliate content production), accounting, control/audit. A three-member board (COO, CFO, Controller) sits between the founder and the departments — see `shared/board.md`.

## Commands

Every Next.js project (client or product) is self-contained, each with its own `package.json` scoped to its own subfolder. **For development, `cd` into the specific project before running anything** — there is still no lint or test at the repo root, and no workspace/monorepo tooling.

**The one exception, added 2026-08-27: a deploy shim.** The repo root now has a `package.json` whose *only* script is `build`, which `cd`s into `products/affiliate-sites/fragrance-dupes` and builds it, plus a root `wrangler.jsonc` pointing at that project's `out/`. This exists solely because Cloudflare runs `npx wrangler deploy` from the repo root when a project has no "root directory" set — two builds failed with *"Could not detect a directory containing static files"* before this existed. It is **not** a workspace root, has no dependencies, and must not grow into a build system: a second deployable site gets its own Cloudflare project with a root directory configured, not a competing root config. See `departments/web-development/CLAUDE.md` for the deploy settings.

Real projects exist today under `products/web-templates/`: `agency-landing/`, and three deliberately distinct fragrance e-commerce templates — `fragrance-store/` (warm cream/gold, rounded), `fragrance-store-2/` ("Nocturne" — dark obsidian/ember-red, sharp corners), `fragrance-store-3/` ("LUMEN" — cool mineral-stone/warm ivory, electric-lavender accent). Each new template's design direction is checked against the others' actual palette/typography before committing, specifically to avoid a third re-skin. Plus `products/affiliate-sites/fragrance-dupes/` (see its own CLAUDE.md). Inside any of them: `npm install`, then `npm run dev` / `npm run build` / `npm run lint`. No test script is configured in any project yet — don't invent one; verify by running the app and asserting against real output. The same self-contained pattern applies once the `new-web-client` skill scaffolds a client under `departments/web-development/clients/<slug>/`.

**Never run `npm run build` while `npm run dev` is live in the same project directory.** Both write `.next/` and the collision corrupts the webpack manifest badly enough that the dev server starts 404ing every route. Recovery: kill both processes, `rm -rf .next`, then run one at a time. Documented for real in `products/affiliate-sites/fragrance-dupes/README.md` after it happened there, but it applies to every Next.js project in this repo.

Setting the workspace up on a different machine (tool installs, `gh`/Claude Code auth, MCP approval): see `SETUP.md`.

A `web-developer` build hit this mid-task and self-healed by re-running the installs. Same class of problem as the "Two physical machines" gotcha below, different mechanism (gitignored-by-design, not a wrong hardcoded path) — don't trust this doc's "installed" claim alone; if a session needs one of these two skills and `.claude/skills/<name>/` isn't actually there, re-run `npx skills@latest add <repo>` (with `--skill design-taste-frontend` for that one) on the machine/environment you're actually on.
- **Git remote**: this repo pushes to `https://github.com/arincaslan/sirketim` (GitHub CLI `gh` is installed and authenticated as `arincaslan`). The repo is **public**, not private — a deliberate tradeoff made to unblock claude.ai's GitHub connector (it only had public-repo scope), so treat the ledger and every department's strategy docs as publicly visible. Two claude.ai scheduled routines (`Sirketim Weekly Accounting Report`, `Sirketim Weekly Control/Audit Report`) run weekly against `main` via `board-cfo`/`board-controller`, writing into `departments/accounting/reports/` and `departments/control/reports/` and pushing directly — a `git pull` may surface new files you didn't create locally.
- **Cross-session sync (do this first, every session)**: the founder works from multiple Claude Code surfaces (this CLI, claude.ai web/mobile). Board subagents (`board-coo`, `board-cfo`, `board-controller`) have no Bash/git tool access — they only ever see whatever is already sitting in the local working tree's files when they're invoked. They cannot discover work that landed on a remote branch. So at the start of a session, and before answering any "what's going on" / status question or delegating to the board, run `git fetch origin` and check `git branch -r` plus `git log main..origin/<branch>` for real work sitting on unmerged branches (commonly named `claude/*` from other sessions). Surface or merge what you find before trusting the board's picture of current state — otherwise their report will be stale by exactly however much cross-session work hasn't synced to `main` yet.
- **Two physical machines, two different Windows usernames — a real, recurring path gotcha**: the founder works from two computers, one logged in as Windows user `win10`, the other as `Semih`. This repo is machine-portable (it's just git), but any **absolute local path this repo's code or docs hardcode** (`C:\Users\<name>\...`) is NOT portable across the two — it's silently wrong on whichever machine didn't write it. This already happened for real: `departments/architecture/lib/cadgen/export_dwg.py`'s `ODA_EXEC_PATH` was written against a `C:\Users\Semih\...` install and broke on the `win10` machine until caught and fixed (see `departments/architecture/CLAUDE.md`'s DWG-conversion gotcha and `departments/architecture/reports/cad-tooling-gap-analysis.md`). After any `git clone`/`git pull` on either machine, and before trusting a hardcoded local install path anywhere in this repo (Python scripts, department CLAUDE.md snippets, anything under `C:\Users\...`), check whether it matches `$env:USERNAME`/`whoami` on the machine you're actually on — if it names the other user, re-verify the real local install path on this machine and update the code/doc, don't assume it still resolves. This applies to any future per-user tool install (not just ODA File Converter) — machine-wide/system installs avoid the problem entirely when available; per-user installs need this check.
- **Before building on any payment, payout, or affiliate provider, check `departments/accounting/CLAUDE.md` first.** Sirketim is a **Turkey-based A.Ş.**, and Turkey is excluded from several providers most stacks treat as defaults. Confirmed unusable: **Stripe** (verified 2026-08-26 against `stripe.com/global` — Turkey absent from ~50 countries, no waitlist), **PayPal** (not operating in Turkey), **Gumroad** (its only two payout rails are PayPal and Stripe Connect). Confirmed usable: **Paddle** (merchant of record, ~10.2% all-in at low volume — a flat ~$15 wire fee dominates), **iyzico**/**PayTR** (Turkish, TRY, both support recurring), **Payoneer** (the rail for USD/GBP/EUR affiliate income, and the documented workaround for networks that cannot pay a TRY account). This is a **real mistake that already happened**: a full Stripe checkout + webhook integration was built for `products/affiliate-sites/fragrance-dupes/` in 2026-08-26 *after* this repo had already documented (2026-08-24) that Stripe does not serve Turkey — the repo knew and the assumption was never checked against it. The cost was recoverable only because no database existed yet. Same failure class as the hardcoded-path gotcha above: the answer was already written down, in another department's file.
- **Know which subagent has web access before delegating research.** `board-cfo`, `board-coo`, `board-controller`, `accountant` and `auditor` have **no `WebSearch`/`WebFetch`** — they can only reason from their training cutoff plus what is already on disk. Delegating "research provider X" to them yields confident, well-structured output whose provider facts may be months stale. This is not hypothetical: `departments/accounting/reports/payment-rails-investigation.md` correctly flagged **9 items it could not verify**, four of which the top-level session then checked live — and **two findings changed** (Amazon direct deposit to a Turkish bank turned out to be genuinely unavailable; Paddle turned out to be genuinely available). Handle it by having the agent flag unverifiable claims explicitly, then verifying them from the top level (which does have web access) before anyone builds on them. Also beware the summarizer inside `WebFetch`: one fetch this session claimed Turkey was eligible for EUR payouts "through the Eurozone programme", which is simply false — sanity-check a fetched answer against what you already know before recording it as fact.

## Architecture

CLAUDE.md files nest and each layer adds scope, not a replacement: this root file -> `departments/<dept>/CLAUDE.md` -> `departments/<dept>/clients/<slug>/CLAUDE.md` (created per-client by a skill), and for one product `products/affiliate-sites/fragrance-dupes/CLAUDE.md`. Read the relevant chain before doing department or client work, don't rely on the root file alone.

- **Subagents** (`.claude/agents/`) map 1:1 to departments — `web-developer`, `architecture-assistant`, `sales-strategist`, `ad-strategist`, `communication-strategist`, `content-strategist`, `accountant`, `auditor`. Each is scoped to its department's CLAUDE.md, has only the tools that department needs, and should be invoked for department-specific work instead of doing it ad hoc from root.
- **Verify a subagent's claimed output before reporting it as done.** A subagent's summary describes what it *intended* to do, which is not always what it did. Confirmed here 2026-08-26: `board-coo` reported writing a specific plan doc and delegating sections to three department subagents, in convincing detail — and no file existed anywhere (`Glob` for the path, `git status`, no trace of the delegated runs). The risk concentrates in **multi-layer delegation** (top level -> board member -> department subagents), because the intermediate layer's own report is the only thing coming back up. After any agent claims to have written a file, check it independently (`Glob` the path, `git status --short`, or `Read` it back) before relaying success or building on top of it. For a single cohesive document, writing it directly is often the better trade than another delegation layer. Subagents that *did* verify their own writes in the same session (`communication-strategist`, `ad-strategist`, both explicitly instructed to read the file back) produced real, correct output — so the instruction to self-verify is worth including in the prompt. **The stronger fix, proven 2026-08-26: run the leaf subagents read-only and text-return-only.** Briefed that way, `board-coo` had `web-developer` and `communication-strategist` return their sections as text without writing anything, then verified their load-bearing claims against the real files itself (8 of 8 confirmed) and reported honestly that no file existed yet. Nothing can be fabricated as "written" when nothing was supposed to be written, and the intermediate layer becomes a checker instead of an unverifiable relay. Prefer this shape whenever the deliverable is one synthesized document rather than parallel edits to separate files.
- **Board members** (`.claude/agents/board-*.md`) are a layer above departments, not an 8th/9th department — `board-coo` (owns web development, architecture, sales, advertising, communication, content), `board-cfo` (owns accounting), `board-controller` (owns control/audit). The founder briefs a board member with an outcome; it delegates to the department subagent(s) it owns via the Agent tool and reports back a synthesized result. See `shared/board.md`. Prefer addressing the board member over the department subagent directly when the request is an outcome rather than a specific department task.
- **Skills** (`.claude/skills/`) are the repeatable intake-to-deliverable workflows: `new-web-client`, `project-brief` (architecture), `client-proposal` (sales), `campaign-brief` (advertising), `product-listing` (sales/products), `affiliate-content` (content — niche → content plan → long-form draft → SEO/schema metadata, set up 2026-08-24 for the affiliate-sites initiative). Prefer these over freeform work when a task matches one.
- **`products/`** vs **`departments/<dept>/clients/`**: products are Sirketim's own sellable goods (web templates, architecture plan packs, POD prints), built by whichever department creates the underlying asset but sold by sales via marketplaces — separate from client-commissioned work. See `products/README.md` for the line breakdown.
- **`products/affiliate-sites/fragrance-dupes/` ("PARFUMOZA") is the most complex codebase in this repo and the only one with its own `CLAUDE.md` — read it before touching that project.** It began as an affiliate content site and is mid-pivot into a two-sided marketplace (producers pay to list dupes; the founder approves each submission; revenue from subscriptions plus commission on dupes *and* originals). It is consequently the first project here to carry a **backend** — though as of 2026-08-27 what survives is `prisma/schema.prisma` (Postgres, not migrated) and Auth.js models; the Stripe checkout/webhook routes were **deleted**, and `app/api/` no longer exists. Planning lives in its `MARKETPLACE-PLAN.md`, `PRODUCER-PROGRAM.md`, and — as of 2026-08-26 — **`FINALIZATION-GUIDE.md`, which is the current ordered roadmap and the right place to start** (6 phases, department owners, costs, dependencies; also published as a dashboard-linked Artifact). Its non-obvious invariant: the displayed match score is *not* the raw computed one (a producer copying the original's notes verbatim would otherwise score exactly 100%) — see that project's CLAUDE.md before changing anything scoring-related.

  It also has a **producer subscription surface** (`/producers`, `/producers/pricing`, `/producers/login`, and a server-gated `/producers/submit`), 68 reference fragrances across 8 houses, and a provider-agnostic `PaymentProvider` enum in its schema. Three things about it are counter-intuitive enough to state here:

  - **The catalog is real but the listings are empty on purpose.** `DUPES`, `REVIEWS` and `affiliateLinks` were all emptied on 2026-08-27 after the listed products turned out not to exist and the reviews turned out to be invented testimonials about real, named companies. Every empty state renders correctly; **do not hand-write entries back in.**
  - **`/producers/submit` is unreachable in production for anyone at all** — its gate requires `NODE_ENV === "development"`, which the bundler inlines at build time, so every discussion of producer tiers is downstream of that. Deliberately unreachable rather than insecure, but don't plan around it being live.
  - **The site has no dynamic server surface** — no `cookies()`/`headers()`/`force-dynamic`, and exactly one route handler (`/go/[slug]`, a static-map 302). It is statically exportable, which is what makes free hosting a real option rather than a compromise.
- **`internal/dashboard/`** — the founder's single-page task board + charts (real assigned/fulfilled tasks per department, financial chart from the ledger, department report links). There is no server, build, or `package.json` here — it's static. Two files, two different edit paths depending on which surface you're in:
  - `internal/dashboard/design/Main.dc.html` + `canvas.json` — a **Claude Design canvas**, editable/previewable through Claude Desktop's Design canvas editor, republished from there via its own Save flow. Treat this as the reference/documentation copy of the task list.
  - `internal/dashboard/design/sirketim-dashboard.html` — a **plain, dependency-free static HTML/CSS/JS file**, hand-written (not generated) 2026-08-24 after `Main.dc.html`'s normal re-seed step (`seed-canvas.mjs` + the `design` skill) proved unavailable from a CLI session — that tooling appears to be Desktop-only. This file is what's actually published to the live Artifact URL from a CLI session: edit it directly, then `Artifact` publish (action `publish`, same `file_path`, passing the existing artifact's `url` so it updates in place rather than forking a new one — see memory `reference_dashboard_artifact_url`, or `Artifact` action `list` if that's gone stale). It reimplements the same data/board with independently-scrolling status columns, clamped task notes with a working expand toggle, a live search box, department filter, and a light/dark theme toggle — genuinely interactive, not templated markup.
  - **These two files can drift** — updating one does not update the other. When a task changes, update both: add/edit the entry in `Main.dc.html`'s `realTasks` array (keeps the Desktop-editable canvas current) and mirror the same entry into `sirketim-dashboard.html`'s `TASKS` array (keeps the live published page current) — matching `id`s make the two easy to diff against each other. Every task assigned or completed in a session should be reflected in both before the turn ends, per the founder's standing instruction.
- **`shared/clients.md`** is the single cross-department client/lead registry (a client can span multiple departments). **`shared/board.md`** is the board charter (who's on it, what they own). **`shared/brand.md`** is Sirketim's own brand/voice, still a placeholder.
- **Connector status** lives in two places: `.mcp.json` (MCP servers, e.g. `openart`) and each department's CLAUDE.md "Recommended connectors" section (everything else, mostly not yet configured — check before assuming a connector is live).

## Conventions

- Client work: `departments/<department>/clients/<slug>/`. Products: `products/<line>/<slug>/`. Slugs are lowercase-hyphenated.
- Register every client/lead in `shared/clients.md` as soon as they're qualified.
- Every transaction (income, expense, subscription charge) gets a row in `departments/accounting/ledger.md` when it happens, not retroactively at report time.
- Don't claim a connector, deploy, or post happened if it isn't actually configured — say what's missing instead.
- **The same honesty rule applies to shipped UI, not just to what you tell the founder.** A feature whose backing service doesn't exist yet should be built and then say so plainly at the point of use — an explicit "not live yet, nothing was saved" state, or an API route returning 503 with a reason. Never a fake success. `products/affiliate-sites/fragrance-dupes/` does this in several places (review form, producer submission form, Stripe routes); those states are requirements, not placeholders to tidy away. A form that silently discards what someone typed is the user-facing version of claiming a connector works when it doesn't.
- **Fixture and placeholder data must be labelled as such in the file that holds it**, with what would make it real. This repo's data is overwhelmingly illustrative right now (fragrance catalogs, producer listings, customer reviews, every affiliate destination), and unlabelled fixtures read as fact to the next session. Where fabricated data would be actively harmful if published — invented customer reviews, for instance — say that too.
- **These CLAUDE.md files go stale faster than the code, and they go stale *confidently*.** A `/init` pass on 2026-08-27 found six separate claims in `products/affiliate-sites/fragrance-dupes/CLAUDE.md` that described a tree that no longer existed — routes documented as absent had been built, a backend documented as "inert, returns 503" had been deleted outright, and three data arrays documented by their contents had been emptied. Each was written accurately and then simply not revisited. The risk is specific: a stale doc reads exactly like a current one, and a future session will plan around "there is no `/fragrance/[slug]`" without ever checking. So **when a change makes a documented claim false, update the doc in the same change** — and treat any concrete claim in these files (a file exists, a count, a route, "this returns 503") as a *hypothesis to verify* rather than a fact, especially before building on it. Grepping the actual tree takes seconds; the four department reports and this file's own history show how expensive the alternative is.
- **A label in the data file does not protect the UI that renders it.** `products/affiliate-sites/fragrance-dupes/lib/reviews.ts` carried an explicit header saying "Do not present these as genuine customer reviews on a live site" — and the component rendered those same six invented reviews with author names, star ratings, dates and an aggregate average, under a heading reading "Reviews from people who bought…", with no fixture label anywhere on screen. The warning was written and then not honoured by the code one file away. **When fixture data is about real, named third parties, it is a different category of risk than illustrative specs** — those six reviews name real operating companies and include a negative one, which is an FTC Fake Reviews Rule and trade-libel exposure rather than a tidiness problem. So: label the fixture in the file *and* make the rendered surface say it, or don't render it at all.
